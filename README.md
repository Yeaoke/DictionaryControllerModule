# DictionaryControllerModule

Модуль загрузки 64 справочников НСИ Минздрава в PostgreSQL: 63 таблицы из V2
и `direction_type` (`1.2.643.5.1.13.13.11.1009`). Java 21, Spring Boot, JDBC, Flyway.

## Единый модуль загрузки

Для всех справочников используется одна цепочка:

```text
SyncController → SyncService → NsiSourceClient
                     ↓
                 SyncStore
                     ↓
            DictionaryApplyService
                     ↓
                  PostgreSQL
```

`DictionaryCatalog` описывает OID, ключи и поля любого справочника,
`SourceValues` преобразует значения. В Java нет отдельных обработчиков,
DTO или условий по имени `direction_type`. Прежние пакеты `dictionary`,
`integration/nsi`, `loading` и `staging` удалены; рабочий код загрузки находится
в пакете `com.example.app.sync`.

Для одного справочника используется общий маршрут
`POST /api/dictionaries/{name}/sync`, для всех — `POST /api/dictionaries/sync`.
`direction_type`, `icd10`, `patient_sex` и остальные отличаются только записью
в каталоге. Особенности столбцов staging задаются необязательным `staging`:

```json
{
  "target": "display_order",
  "type": "numeric(10)",
  "source": "SORT",
  "staging": "sort"
}
```

Без `staging` используется имя `target`. Поэтому существующая БД не требует
переименования столбцов для перехода на общий загрузчик.

## Возможности

- Получение всех страниц выбранной версии без ограничения списка полей.
- Загрузка текущего паспорта, всех страниц списка версий и паспортов исторических
  версий. Уже сохранённые исторические паспорта повторно не скачиваются.
- Сохранение исходных JSON-страниц, включая неизвестные типизированной схеме поля.
- Заполнение всех полей источника, описанных в существующих SQL-таблицах.
  Сопоставления перечислены явно в `src/main/resources/dictionary-catalog.json`.
- Составные ключи, даты, числа, логические значения; проверка структуры паспорта.
- Атомарное обновление типизированного справочника и его staging-таблицы:
  новые записи добавляются, существующие обновляются/восстанавливаются,
  отсутствующие получают `is_deleted='Y'`.
- Локальные `search_synonym` и `display_order`, не связанные с полем источника,
  сохраняются при обновлении существующих записей.
- Пропуск уже загруженной версии, принудительное обновление и явная загрузка
  конкретной версии. Историческая версия, явно выбранная для загрузки, становится
  текущей в типизированной таблице.
- Фоновая очередь, журнал запусков, защита от одновременной загрузки одного
  справочника, API чтения данных и результатов.

По умолчанию загружаются **актуальные данные и метаданные всех версий**.
Автоматическая выгрузка всех исторических наборов строк не выполняется.
Исходные страницы каждой выполненной загрузки остаются в БД.

## Подготовка и запуск

Нужны JDK 21, PostgreSQL (проверено на 18.3), база `dsa`, пользователь БД и ключ
НСИ с доступом к выбранным справочникам. Пользователю БД нужны права создания
схем и объектов миграций; для обновления существующей установки — владение
изменяемыми объектами или соответствующие полномочия.

В **cmd.exe**, из корня именно этой копии репозитория:

```bat
set "JAVA_HOME=C:\Program Files\Java\jdk-21.0.11"
set "POSTGRES_URL=jdbc:postgresql://localhost:5432/dsa"
set "POSTGRES_USERNAME=postgres"
set "POSTGRES_PASSWORD=ВАШ_ПАРОЛЬ"
set "NSI_USER_KEY=ВАШ_КЛЮЧ"
mvnw.cmd spring-boot:run
```

В **PowerShell**:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21.0.11'
$env:POSTGRES_URL = 'jdbc:postgresql://localhost:5432/dsa'
$env:POSTGRES_USERNAME = 'postgres'
$env:POSTGRES_PASSWORD = 'ВАШ_ПАРОЛЬ'
$env:NSI_USER_KEY = 'ВАШ_КЛЮЧ'
.\mvnw.cmd spring-boot:run
```

Значения задаются в том же терминале, где запускается приложение.
Для запуска из IDE задайте их в Environment variables конфигурации запуска.
Файл `.env` сам по себе Spring Boot здесь не читает.

Flyway применит V6 поверх уже установленных V1–V5 либо все миграции на пустой
базе. V1–V5 не изменены. Приложение останется работать на
`http://127.0.0.1:8080`; при старте справочники автоматически не скачиваются.
Без `NSI_USER_KEY` можно запустить приложение и просматривать ранее загруженные
данные, но новые загрузки завершатся с понятной ошибкой.

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `POSTGRES_URL` | `jdbc:postgresql://localhost:5432/dsa` | База данных |
| `POSTGRES_USERNAME` | обязательна | Пользователь БД |
| `POSTGRES_PASSWORD` | обязательна | Пароль БД |
| `NSI_USER_KEY` | пусто | Ключ для запросов НСИ |
| `NSI_PAGE_SIZE` | `500` | Размер страницы, 1–1000 |
| `NSI_MAX_PAGES` | `100000` | Максимум страниц на один список |
| `SERVER_ADDRESS` | `127.0.0.1` | Интерфейс HTTP-сервера |
| `SERVER_PORT` | `8080` | HTTP-порт |

API предназначен для локального/доверенного административного использования:
встроенной аутентификации нет, `userId` — атрибут аудита, а не проверенная
учётная запись. Для сетевого размещения подключите аутентификацию и разграничение
доступа на сервере или шлюзе до изменения `SERVER_ADDRESS`.

## Первая загрузка

Примеры ниже — **PowerShell**; приложение должно работать в другом терминале.

```powershell
$api = 'http://127.0.0.1:8080/api'

# Каталог: имена, OID, ключи, сопоставления полей, локальные версии.
Invoke-RestMethod "$api/dictionaries"

# Один справочник. userId укажите свой; внешняя users_v новому загрузчику не нужна.
$run = Invoke-RestMethod "$api/dictionaries/direction_type/sync" `
    -Method Post -ContentType 'application/json' `
    -Body '{"userId":1}'

# Статус: queued -> running -> success / skipped / failed.
Invoke-RestMethod "$api/sync-runs/$($run.runId)"

# Полученные записи.
Invoke-RestMethod "$api/dictionaries/direction_type/rows?limit=100&offset=0"
```

Загрузить все 64 справочника:

```powershell
$runs = Invoke-RestMethod "$api/dictionaries/sync" `
    -Method Post -ContentType 'application/json' `
    -Body '{"userId":1}'
$runs | Format-Table
```

Ответ HTTP 202 означает принятие в очередь, а не успешную загрузку.
Каждый элемент содержит свой `runId`; ошибки одного справочника не отменяют
остальные. Справочник с активным запуском возвращается как `already_active`.
Очередь обрабатывается одним рабочим потоком; допускается до 128 ожидающих задач.

Параметры тела:

```json
{
  "userId": 1,
  "version": "1.2",
  "force": true,
  "allowEmpty": false
}
```

`version` можно не задавать: выбирается версия текущего паспорта. Для массовой
загрузки общую `version` задавать нельзя. `force` разрешает повторную загрузку
той же версии. `allowEmpty=true` разрешает применить подтверждённый паспортом
пустой набор, пометив существующие записи удалёнными; по умолчанию это запрещено.

## API

| Метод и путь после `/api` | Результат |
|---|---|
| `GET /dictionaries` | Каталог всех 64 справочников |
| `POST /dictionaries/{name}/sync` | Поставить один справочник в очередь |
| `POST /dictionaries/sync` | Поставить все справочники в очередь |
| `GET /sync-runs/{id}` | Статус, версия, счётчики и ошибка |
| `GET /dictionaries/{name}/runs` | История запусков |
| `GET /dictionaries/{name}/rows` | Типизированные записи |
| `GET /dictionaries/{name}/versions` | Сохранённые метаданные версий |
| `GET /dictionaries/{name}/passport?version=1.2` | Сохранённый паспорт версии |
| `GET /sync-runs/{id}/pages/data/0` | Полный JSON страницы данных |
| `GET /sync-runs/{id}/pages/versions/0` | Полный JSON страницы версий |
| `POST /sync-runs/{id}/recover` | Освободить зависший/ожидающий запуск |

Списки поддерживают `limit` (1–1000) и `offset` (от 0). Для `/rows` параметр
`includeDeleted=true` включает удалённые записи. Без `version` паспорт берётся
для локально загруженной версии. Список версий сортируется лексикографически:
порядок списка не используется для определения актуальности.

Ошибки API: 400 — неверные параметры; 404 — неизвестный объект; 409 — конфликт
запусков; 503 — очередь/БД недоступна. Ошибка выполнения фоновой загрузки
возвращается через статус `failed` и `error_message` в журнале.

## Как обеспечивается целостность

1. Запуск фиксируется в БД до помещения в очередь. Частичный уникальный индекс
   запрещает два активных запуска одного справочника, в том числе из разных процессов.
2. Рабочий поток удерживает сессионную PostgreSQL-блокировку справочника.
3. Проверяются OID, версия и наличие всех сопоставленных полей в паспорте.
   Данные запрашиваются с фиксированной версией, начиная со страницы 0.
4. Все исходные страницы сохраняются по мере получения. Число строк сверяется
   с `rowsCount` паспорта. Пустая преждевременная страница вызывает ошибку.
5. Повторный паспорт выбранной версии проверяется перед применением.
6. Отдельная транзакция заполняет временную типизированную таблицу. Дубликаты
   ключей, NULL в обязательных полях, нарушение CHECK, переполнение чисел
   или неверные даты откатывают применение целиком.
7. В одной транзакции обновляются целевая таблица, staging, локальная версия
   и успешный статус запуска. Паспорт и исходные страницы не откатываются:
   они остаются для диагностики.

`rows_updated` — количество совпавших ключей, включая строки без изменения
значений. `rows_deleted` — число записей, впервые помеченных удалёнными в этой
загрузке. Даты с часовым поясом приводятся к UTC для столбцов
`timestamp without time zone`; локальные даты сохраняются без преобразования.

При аварийном завершении процесса журнал может остаться в `queued`/`running`.
После перезапуска вызовите `/recover` для такого запуска и отправьте загрузку
повторно. Этот метод не останавливает активную загрузку: если другой процесс
удерживает блокировку, будет возвращён 409. Ожидающую задачу можно таким образом
отменить до её старта. Автоматическое продолжение с середины не выполняется.

## Схема данных и совместимость

Типизированные таблицы `data.<name>` и `data.dsa_raw_<name>` сохраняют назначение.
`data.dsa_loaded_version` хранит последнюю успешно применённую версию.

Журнал загрузок — `data.dsa_load_batch`. V7 переносит в него все записи
`nsi_sync_run`, сохраняет UUID и связи страниц, затем удаляет прежнюю таблицу.
Числовой `id` журнала сохраняется; `run_id` — UUID для API.
API возвращает его как `id`, а числовой ключ — как `batch_id`.
Версия записывается в `new_version`, число полученных строк — в `rows_extracted`.
В API эти поля по-прежнему называются `source_version` и `rows_received`.
Статусы общего загрузчика: queued, running, success, skipped, failed, interrupted.
`load_procedure_name` пуст для Java-загрузки; `loaded_by` содержит ID пользователя.

Дополнительные таблицы:

- `data.nsi_sync_page` — исходные страницы, связанные с `dsa_load_batch.run_id`.
- `data.nsi_dictionary_passport` — паспорта по справочнику и версии.
- `data.nsi_dictionary_version` — метаданные версий.

Общий загрузчик не вызывает старые процедуры V4/V6 и не требует
`access_work.users_v`, `data.log_level` и `data.system_log`.
Миграции V1–V6 не изменены. При обновлении остановите старую версию приложения:
после V7 она не сможет обращаться к прежнему журналу.
Вместо ручного `CALL load_direction_type` используйте общий API загрузки.

Поля источника, отсутствующие в типизированной таблице, доступны в исходных
страницах. Новое поле для SQL-запросов добавляется новой миграцией и записью
в каталоге. Для `direction_type` V6 дополнительно сохраняет `DOC` в целевой таблице.

Каталог основан на сопоставлениях в исходных SQL-комментариях. Для
`foms_classification_criterion.valid_from` и `foms_consilium_purpose.valid_from`
используется `DATEBEG`; для `personal_account_income_admin` — одноимённое поле.
Эти сопоставления проверяются по паспорту при загрузке. Если источник изменил
имя поля, загрузка завершается ошибкой вместо молчаливой потери данных.

Файлы в `resources/sql` — исходные описания; Flyway исполняет только
`resources/db/migrations`. `scripts/build-catalog.cjs` воспроизводит исходный
каталог из V2 и определения `direction_type`; не запускайте его поверх вручную
обновлённого каталога без проверки diff.

## Проверки

```powershell
.\mvnw.cmd test
```

Без `TEST_DATABASE_URL` выполняются модульные и HTTP-контрактные тесты;
интеграционные тесты пропускаются. Для полного прогона на Windows:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21.0.11'
.\scripts\test-postgres.ps1
```

Скрипт создаёт отдельный временный кластер в `target`, запускает его только на
`127.0.0.1:55439`, выполняет тесты и останавливает сервер в `finally`.
Рабочая база `dsa` не используется. Путь к PostgreSQL и порт можно изменить
параметрами `-PostgresBin` и `-Port`. Остатки остановленного тестового кластера
можно удалить вместе с обычными артефактами сборки.

На другой ОС укажите `TEST_DATABASE_URL`, `TEST_DATABASE_USER`,
`TEST_DATABASE_PASSWORD` для **отдельной одноразовой базы** и выполните `mvn test`.
Интеграционные тесты создают схему миграциями и очищают тестовые данные.

Проверяется применение V1–V6, соответствие всех 64 таблиц каталогу и staging,
запись всех типизированных полей, составные ключи, мягкое удаление, сохранение
локальных полей, откат при дубликатах/пустом снимке, страницы и метаданные,
пропуск той же версии, защита от параллельных запусков и восстановление очереди.

HTTP-контракт тестируется локальным сервером и фикстурами. Реальная выгрузка
всех 64 справочников с рабочим ключом НСИ не входит в автоматические тесты.
Первую реальную загрузку начните с одного справочника, проверьте журнал,
паспорт и строки, затем запускайте остальные.
